# Test quality

Examples for the `tdd` skill: tests worth keeping, tests that will hurt, and where mocks belong. TypeScript here, but the patterns carry to any language.

## Test through the interface a caller uses

```typescript
// Good: asserts what a caller observes
test("user can checkout with a valid cart", async () => {
  const cart = createCart();
  cart.add(product);

  const result = await checkout(cart, paymentMethod);

  expect(result.status).toBe("confirmed");
});
```

It survives a rewrite of the checkout internals, and its name says what the system does.

```typescript
// Fragile: asserts how the code is wired
test("checkout calls paymentService.process", async () => {
  const processSpy = jest.spyOn(paymentService, "process").mockResolvedValue({ ok: true });

  await checkout(cart, payment);

  expect(processSpy).toHaveBeenCalledWith(cart.total);
});
```

This one breaks when the payment call moves, even though the behavior is unchanged. Write it only when "charged exactly once" is the behavior you care about, and name it that way.

## Verify through the interface, not a side channel

```typescript
// Fragile: reaches past the interface into storage
test("createUser saves to the database", async () => {
  await createUser({ name: "Alice" });

  const row = await db.query("SELECT * FROM users WHERE name = ?", ["Alice"]);
  expect(row).toBeDefined();
});

// Good: round-trips through the interface
test("createUser makes the user retrievable", async () => {
  const user = await createUser({ name: "Alice" });

  const retrieved = await getUser(user.id);
  expect(retrieved.name).toBe("Alice");
});
```

The second version still fails if persistence breaks, and keeps passing when the schema changes.

## Expected values must be independent

```typescript
// Weak: the expectation repeats the implementation's own logic
test("calculateTotal sums line items", () => {
  const items = [{ price: 10 }, { price: 5 }];
  const expected = items.reduce((sum, item) => sum + item.price, 0);

  expect(calculateTotal(items)).toBe(expected);
});

// Good: the expectation is a known literal
test("calculateTotal sums line items", () => {
  expect(calculateTotal([{ price: 10 }, { price: 5 }])).toBe(15);
});
```

The first version still catches crashes and type errors, but it cannot catch a
mistake in the summing rule itself, because the test reproduces the same rule. A
wrong discount or rounding decision is duplicated in the expectation and passes.

Snapshots generated by the code under test and constants imported from the
implementation have the same weakness: whatever the code believes, the expectation
believes too.

## Where to mock

Mock at the edge of your system:

- Third-party APIs: payments, email, search, anything over the network you do not own.
- Clock and randomness.
- The filesystem, sometimes.
- Databases, sometimes. A real test database gives a better signal when the project already runs one.

Do not reflexively mock your own modules and collaborators. Replacing internal parts with mocks means the test verifies the wiring you imagined rather than the behavior you shipped.

Internal fakes earn their place when the real collaborator is slow, non-deterministic, or needs setup out of proportion to the test. That is a tradeoff to make on purpose, not a default.

## Designing for mockable boundaries

Accept dependencies instead of constructing them:

```typescript
// Substitutable
function processPayment(order, paymentClient) {
  return paymentClient.charge(order.total);
}

// Pinned to one implementation and one environment variable
function processPayment(order) {
  const client = new StripeClient(process.env.STRIPE_KEY);
  return client.charge(order.total);
}
```

Prefer one function per external operation over a single generic caller:

```typescript
// Each operation is independently substitutable
const api = {
  getUser: (id) => fetch(`/users/${id}`),
  getOrders: (userId) => fetch(`/users/${userId}/orders`),
  createOrder: (data) =>
    fetch("/orders", {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify(data),
    }),
};

// One entry point means conditional logic inside every fake
const api = {
  fetch: (endpoint, options) => fetch(endpoint, options),
};
```

With one function per operation, each fake returns one shape, and the test setup shows which external calls the test actually exercises.
